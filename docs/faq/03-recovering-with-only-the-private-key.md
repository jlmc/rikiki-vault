# I lost my SSD, the remote is up to date, but I only backed up `private.key`, not `public.key` — how do I recover?

*[Ler em português](03-recovering-with-only-the-private-key.pt.md)*

Harder than [the previous case](02-recovering-with-both-keys-backed-up.md), but not necessarily
lost — you have two paths. If any other machine (or person) still has access to the vault, take
**Path A**: it's simple and always works. If this was your only machine, **Path B** can still
recover your exact original identity, but it depends on external tooling and isn't guaranteed.

## Why this is harder

The app treats `private.key` and `public.key` as an inseparable pair on disk — `LocalKeyStoreAdapter`
requires *both* files to exist before it will load an identity at all. A lone `private.key`, on its
own, isn't something the app can use: place it alone in `~/.rikiki-vault/identity/` and the
identity still won't be recognized as existing. There is no built-in "regenerate my public key"
command.

## Prerequisites (both paths)

On a genuinely bare replacement machine (macOS with [Homebrew](https://brew.sh/) installed):

```bash
brew install openjdk@25 maven git
sudo ln -sfn "$(brew --prefix openjdk@25)/libexec/openjdk.jdk" \
  /Library/Java/JavaVirtualMachines/openjdk-25.jdk
export PATH="$(brew --prefix openjdk@25)/bin:$PATH"
java -version   # confirm it reports 25

git clone <this-app's-source-repository-url>
cd rikiki-vault
mvn -pl cli -am package -DskipTests   # produces cli/target/rikiki-vault.jar
```

That last `git clone` is the Rikiki Vault **application's own source code** — a different
repository from your personal vault (the one with your encrypted files), which you'll clone
separately in the steps below. See the main [README](../../README.md) ("Building"/"Distribution")
for building the desktop app instead, or a native installer that doesn't need Java at all. (On
Linux, use your distribution's package manager for JDK 25 + Maven + Git instead of `brew`.)

## Path A — new identity + re-authorization (use this if you can)

The safest option when someone else still has access: don't try to resurrect the old identity at
all. Let the new machine get a fresh one, and have it authorized like any new machine would be.

1. Leave `~/.rikiki-vault/identity/` empty on the new machine (don't place the lone `private.key`
   there — it won't help and could cause confusion later).
2. Clone your personal vault as normal:
   ```bash
   java -jar cli/target/rikiki-vault.jar clone <your-vault-remote-uri>
   ```
   With no existing identity found, the app generates a brand-new keypair for this machine. The
   clone itself succeeds, but nothing decrypts yet — this new key was never authorized.
3. Export the new public key:
   ```bash
   java -jar cli/target/rikiki-vault.jar export-key my-new-machine.pub
   ```
4. Send that file to whoever still has access, and have them authorize it (from any machine that's
   still an authorized recipient):
   ```bash
   java -jar cli/target/rikiki-vault.jar authorize <label> my-new-machine.pub
   ```
   (or "Gerir Acesso" in the desktop app). This re-encrypts every tracked file for the updated
   recipient set, this new machine included.
5. `pull` again — files now decrypt normally.
6. Optionally, once you're confident the old identity is truly gone for good, `revoke` its old
   fingerprint if it's still listed as a recipient, so it can no longer decrypt anything newly
   published.

This path needs at least one other authorized machine or person available. If you were the only
one with access, go to Path B instead.

## Path B — derive the public key from the backed-up private key (works alone)

Unlike some key types, an X25519 public key is a deterministic function of its private key — it
can be regenerated by anyone who has the private key, using ordinary tooling, since it isn't a
secret derivation. The app stores keys as plain PKCS8/X.509 DER (no PEM headers) — unless the
backed-up key is passphrase-protected (see Step 0 below), in which case it's a different,
self-describing "RVPK" envelope that ordinary tooling can't read directly.

### Step 0 — if your backed-up `private.key` is passphrase-protected

Skip this step entirely if it isn't (the commands below already work directly on a plain
PKCS8/X.509 DER file). If it is, you need to decrypt it to plain PKCS8 first, before deriving the
public key. Two ways to do that — pick one:

**Recipe A — the app's own `unwrap-key` command.** You already built `cli/target/rikiki-vault.jar`
in the prerequisites above, so this needs nothing extra. It uses the exact same code that
encrypted the key in the first place, so a wrong passphrase is a real, clear error, not a silent
mistake:

```bash
java -jar cli/target/rikiki-vault.jar unwrap-key /path/to/backup/private.key private.key.plain
# Passphrase: ****************
# Chave privada em claro escrita em private.key.plain
```

**Recipe B — pure OpenSSL/bash, no Java at all**, via
[`scripts/unwrap-private-key.sh`](scripts/unwrap-private-key.sh) (same folder as
`derive-public-key.sh` below):

```bash
docs/faq/scripts/unwrap-private-key.sh /path/to/backup/private.key private.key.plain
# Passphrase: ****************
```

**The trade-off between them:** Recipe A verifies the passphrase cryptographically (AES-GCM's
authentication tag) and fails loudly if it's wrong. Recipe B can't do that check at all (plain
OpenSSL has no way to verify a GCM tag) — a wrong passphrase there produces garbage silently, and
you'll only find out at the next step, when `derive-public-key.sh` either fails to parse it or
produces a fingerprint that doesn't match what you expect. Prefer Recipe A when you have a JDK
handy; Recipe B exists for exactly the same reason Path B itself does — sometimes building the app
isn't an option.

Either way, the rest of this page uses `private.key.plain` (the output of whichever recipe you
ran) wherever it says "the derived/restored `private.key`" — a lone protected `private.key` still
can't be used directly by anything below.

### Deriving the public key

macOS ships `openssl` as LibreSSL by default, which doesn't reliably handle X25519 the same way —
[`scripts/derive-public-key.sh`](scripts/derive-public-key.sh) (in this same `docs/faq/` folder,
so it's already there in the app source you cloned in the prerequisites above) finds Homebrew's
real OpenSSL automatically, and tells you to `brew install openssl@3` first if it can't:

```bash
chmod +x docs/faq/scripts/derive-public-key.sh   # not needed if it kept its permissions from git
docs/faq/scripts/derive-public-key.sh /path/to/backup/private.key public.key
```

Both arguments are **paths** — the first is where your backed-up `private.key` file sits, the
second is where to write the derived `public.key` file (not the content of either, just their
locations). It prints the resulting fingerprint too, so you can immediately compare it against
`vault/recipients.json` (see step 2 below) without a separate `whoami` round trip. Equivalent to
running directly, if you'd rather not use the script:

```bash
openssl pkey -in private.key -inform DER -pubout -outform DER -out public.key
```

(On Linux, your distribution's `openssl` package is almost always genuine OpenSSL already — no
Homebrew step needed.)

Then:

1. **Put both files where they belong** — the recovered `private.key` (`private.key.plain` from
   Step 0 if the backup was passphrase-protected, or your backup as-is otherwise) and the
   `public.key` you just derived — and restrict permissions, as in the [previous
   answer](02-recovering-with-both-keys-backed-up.md#3-restore-the-identity-files):
   ```bash
   mkdir -p ~/.rikiki-vault/identity
   cp private.key.plain ~/.rikiki-vault/identity/private.key   # or your backup directly, if it wasn't protected
   cp public.key ~/.rikiki-vault/identity/
   chmod 700 ~/.rikiki-vault/identity
   chmod 600 ~/.rikiki-vault/identity/private.key ~/.rikiki-vault/identity/public.key
   ```
   The restored identity is unprotected at this point even if the backup wasn't — Step 0 always
   decrypts to plain PKCS8. Run `set-passphrase` again afterward if you want it protected on the
   new machine too.
2. **Run `whoami` and check the printed fingerprint**:
   ```bash
   java -jar cli/target/rikiki-vault.jar whoami
   ```
   If you have a copy of the vault's `vault/recipients.json` (from a still-existing clone, or from
   anyone with access), look there for a matching fingerprint under your machine's old label:
   ```bash
   cat /path/to/an/existing/clone/vault/recipients.json
   ```
   A match confirms the derivation reconstructed the exact original identity.
3. **If it matches**, `clone`/`pull` normally — no re-authorization needed, since it's
   cryptographically the same identity the vault already trusts:
   ```bash
   java -jar cli/target/rikiki-vault.jar clone <your-vault-remote-uri>
   ```
4. **If it *doesn't* match** (wrong OpenSSL version, a subtly different key format, or a corrupted
   backup), don't keep guessing — no more commands here, go back to **Path A** above. Trying more
   tools/flags at this point risks more confusion than it's worth.

### Complete worked example (passphrase-protected backup, both recipes)

Start to finish, on one machine, so you can see every command in order. `123.456.789.10` stands in
for wherever your vault's remote actually is.

```bash
# --- earlier, on the original machine: protect the identity and back it up ---
java -jar cli/target/rikiki-vault.jar set-passphrase
# Nova passphrase: ****************
# Confirma a nova passphrase: ****************
# Passphrase definida.
cp ~/.rikiki-vault/identity/private.key ~/Backups/private.key.protected

# --- disaster: disk dies, public.key is gone, only the backup above survives ---

# --- on the replacement machine, after the Prerequisites steps above: ---

# Recipe A (needs the jar you already built):
java -jar cli/target/rikiki-vault.jar unwrap-key ~/Backups/private.key.protected private.key.plain
# Passphrase: ****************
# Chave privada em claro escrita em private.key.plain

# ...or Recipe B (no Java at all):
docs/faq/scripts/unwrap-private-key.sh ~/Backups/private.key.protected private.key.plain
# Passphrase: ****************
# Written: private.key.plain

# Either recipe leaves the same private.key.plain - derive the public key from it:
docs/faq/scripts/derive-public-key.sh private.key.plain public.key
# Fingerprint: 4f2a9c... (compare this against vault/recipients.json)

# Put both files in place:
mkdir -p ~/.rikiki-vault/identity
cp private.key.plain ~/.rikiki-vault/identity/private.key
cp public.key ~/.rikiki-vault/identity/
chmod 700 ~/.rikiki-vault/identity
chmod 600 ~/.rikiki-vault/identity/private.key ~/.rikiki-vault/identity/public.key

# Confirm, then resume normally:
java -jar cli/target/rikiki-vault.jar whoami
java -jar cli/target/rikiki-vault.jar clone git@github.com:you/my-vault-encrypted.git
```

## Takeaway

This scenario is exactly why [the first answer](01-disk-failure-and-backups.md) recommends backing
up `private.key` **and** `public.key` together: it's one tiny extra file, and it removes any
dependency on correctly deriving a key with the right tool, or on someone else still being around
to `authorize` you.
